\chapter{Filesystem Forensic Chronology}

Chronological event reconstruction forms the backbone of digital forensic analysis. Filesystems store critical metadata timestamps for every inode that allow investigators to establish causal sequences of events. Using the \texttt{mactime} utility from \textit{The Coroner's Toolkit} (TCT) and \textit{The Sleuth Kit} (TSK), the team correlated every disk action with second-by-second accuracy.

\begin{notaforense}[Forensic Timestamps: Demystifying ctime in Unix/Linux]
A frequent misconception among junior examiners is interpreting \texttt{ctime} as file creation time (\textit{birth time}). In classic Unix filesystems (UFS, Ext2, Ext3), a birth timestamp did not exist; it was introduced later in Ext4 and modern filesystems:
\begin{itemize}
    \item \textbf{mtime (Modification Time):} The exact instant the file's data blocks were last modified (e.g., saving changes with an editor or issuing \texttt{write()}).
    \item \textbf{atime (Access Time):} The instant file contents were read (via \texttt{cat}, binary execution, or \texttt{read()}).
    \item \textbf{ctime (Change Time):} The instant the \textbf{inode metadata} was altered (permission changes via \texttt{chmod}, ownership changes via \texttt{chown}, hard link creation/destruction via \texttt{ln}, or file size alterations). While a user or attacker can arbitrarily forge \texttt{mtime} and \texttt{atime} using the \texttt{utime()} system call or \texttt{touch -d}, \textbf{they cannot arbitrarily forge ctime}, which is updated strictly by the kernel based on the system hardware clock.
    \item \textbf{dtime (Deletion Time):} In Ext2, records the precise instant the inode was unlinked from its directory structure via \texttt{unlink()}, marking logical file deletion.
\end{itemize}
\end{notaforense}

\section{Filesystem Timeline Analysis}

The forensic procedure extracts and chronologically sorts modification (\textit{mtime}), access (\textit{atime}), inode status change (\textit{ctime}), and deletion (\textit{dtime}) timestamps across all inodes on the storage media using \texttt{ils} and \texttt{mactime}.

From this collected telemetry, a \emph{comprehensive timeline} of the entire volume was reconstructed, including unallocated inodes whose raw data blocks had not yet been overwritten by subsequent OS operations. Standard \texttt{mactime} syntax follows the format:

\noindent\texttt{Date and Time | Size | MAC Attribute | Permissions | UID | GID | Inode | File Path}

\begin{perspectiva20}[Contemporary Forensic Perspective: From mactime to Super-Timelines with Plaso]
In 2004, \textit{The Coroner's Toolkit} (TCT) and \textit{The Sleuth Kit} (TSK) with \texttt{mactime} represented the zenith of magnetic filesystem timeline reconstruction. Today, contemporary forensics relies on engines like \textit{Plaso / log2timeline}, capable of fusing not only filesystem inode metadata, but browser histories, Windows Event Logs (EVTX), Prefetch execution artifacts, AWS CloudTrail / Azure cloud API logs, and database transaction records into a unified indexed \textit{super-timeline} analyzed via platforms like Timesketch and Elasticsearch.
\end{perspectiva20}
